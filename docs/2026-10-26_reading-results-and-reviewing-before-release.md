# 結果をどう読ませるか、リリース前のレビューにどれだけ待つか

> **2026-10-27 追記（訂正）:** 本書の「Ubuntu の OS の Brotli は修正待ち（`NO_FIX_AVAILABLE`、CVE ページは Needs evaluation、USN なし）」は
> 2026-10-26 の取得時点のもの。Ubuntu は同日 USN-8956-1 で 22.04・24.04・26.04・26.10 を修正し、既知データは 2026-10-27 に全行を
> 一次資料で確かめ直して更新した。正: `docs/design.md`（`design.ja.md`）2.1。経緯: `docs/2026-10-27_path-bytes-mutation-tests-and-data-refresh.md`。
> 本書の「結果の読ませ方」の考え方はそのまま有効。

## Purpose & Context

- 実装（同日の impl 記録）は依頼文に沿って進んだが、本人の短い問いがいくつか入るたびに、
  「ツールが何を言い、利用者がそれをどう受け取るか」と「出荷前の検収にどこまで手間をかけるか」の考えが曲がった。
- きっかけはすべて本人の素朴な問い（「全滅ということ？」「PPA にあっても普通の人は使わないよな？」
  「codex にレビューしてもらわなくていいか？」「2 時間かかっても待つべきだろう？」「みんな自分の環境でチェックできる、という認識で良いか？」）。

## Insight Crystallization

### 1. 結果は「層」で読ませる（OS のコピー／同梱コピー）
- **WHAT:** 「Ubuntu は全滅か」への答えは一語では返せない。OS が配る Brotli は全リリースで修正待ち
  （NO_FIX_AVAILABLE）だが、製品が抱える同梱コピー（Node.js・PyPI など）は OS に関係なく今すぐ直せる。
  利用者は「全滅」か「大丈夫」の二値で読みがちなので、結果の側を二層で見せる必要がある。
- **HOW:** 統合テストの表（5 つの OS × 判定）を見せたところで本人が「Ubuntu は今のところ全滅ということ？」と返した。
  表は正しかったが、読み方が付いていなかった。
- **CONNECTION [in-session]:** 図解 02 の構図（行＝層、列＝OS。上段だけ OS で分かれ、下段は 1 本の帯）と、
  docs/verification の「How to read these results」節はこの問いから作った。
- **CONNECTION [in-session]:** 図解 01 のキーメッセージ「OS の更新が直すのは OS のコピーだけ」も同じ二層の言い方。
- **SCOPE:** この CVE のように「OS 版と同梱版が並存する」部品に効く読み方。単一の配布経路しかない部品には不要。

### 2. 修正候補の「存在」と、利用者にとっての「直せる」は別物
- **WHAT:** 修正候補が試験用 PPA（ubuntu-security-proposed、2026-10-25）にあっても、普通の利用者は使わない。
  判定（NO_FIX_AVAILABLE）は変えず、備考に「試験用 PPA にある」と書くにとどめる。
- **HOW:** サブエージェントの調査に PPA の話が出ていたのを、母艦が自分で Launchpad API を引いて確かめたところで、
  本人が「PPA にあっても普通の人はそれ使わないよな？（笑）」と返した。母艦は「修正が近い」ことを重く見かけていた。
- **CONNECTION [in-session]:** 既知データの (b) 案（PPA の版を `unreleased` で登録し、その版以上なら自動で FIXED）は、
  判定を変えずに「USN が出てデータ更新が遅れる間」だけを救う案として残っている（本人判断待ち）。
- **CONNECTION [recording-time inference]:** Debian sid の「tracker に 1.2.0-4.1 はあるがアーカイブ未着 → 未修正扱い」
  （本人指示）と同じ線引き: 利用者の手元に届く経路に載ったものだけを修正として数える。
- **SCOPE:** 判定の軸は「利用者が普通の手段で入れられるか」。セキュリティ研究者向けの道具なら別の線引きもありうる。

### 3. 全テスト合格の後でも、偽の安心は残っていた（author ≠ reviewer）
- **WHAT:** 単体テスト 80 件超・統合テスト全合格・自動セキュリティレビュー複数回の後に、Codex の途中結論だけで
  実在の欠陥 5 件が出た。うち 2 件（パスやメタデータだけで FIXED、`bcc_judge` が配列を上書きして脆弱なコピーが消える）は、
  依頼文がいちばん避けたい「偽の安心」を生む経路だった。
- **HOW:** 本人が「CI が通ったらリリースも作っちゃってほしいんだが、codex にレビューしてもらわなくていいか？（笑）スキルがあったはずだが」と止めた。
  母艦は CI 待ちからそのままリリースへ進む段取りを書いていた。結果を見て本人「やっぱり。。。レビューしておいて良かったな」。
- **CONNECTION [in-session]:** テストは書き手の想定の範囲しか検査しない。2 件とも「攻撃者が名前や中身を偽る」想定が
  テストに無かった（追加済み）。
- **SCOPE:** 1 例。別系統のレビュアーが毎回同じ割合で見つけるとは言えない。

### 4. レビューの質を時間制限で削らない
- **WHAT:** 「2 時間かかっても、ちゃんとレビューしてくれるなら待つべき」。打ち切りは「指摘なし」ではない。
  途中で切れても中間の結論を回収する。レビュアーが材料を読めない環境（sandbox が動かない）なら、材料を直接渡す。
  範囲を絞り、既知の指摘を除外し、答えの書式を決めると、時間が新しい指摘に使われる。
- **HOW:** 1 回目は 15 分で打ち切り（実は途中結論に 5 件）、2 回目は sandbox がコマンドを実行できずコードを読めないまま
  「unassessed」、3 回目は相手の容量不足。母艦が「タイムアウトの見直し」を言う前に、本人が「向こうでのプロンプトを見直すとともに、
  こちらでの猶予時間にもっと余裕をもたせるようにしておかないか？」と提案した。
- **CONNECTION [in-session]:** codex スキルに反映（2 時間、`--json` で途中結果、sandbox の事前確認と source-in-prompt モード、
  プロンプトの指針）。nagistack CHANGELOG 2026-10-26。
- **CONNECTION [recording-time inference]:** 既存の「effort を黙って下げない」（2026-08-11）と同じ向き: 間に合わせるために
  レビューの質を落とさない。今回は「時間」の側にも同じ原則を広げた形。
- **SCOPE:** 待てるのはリリース前の検収のような区切りの場面。対話的な開発の途中で毎回 2 時間待つ話ではない。

### 5. 読みに来る人の言語に合わせ、何をするツールかを一目で見せる
- **WHAT:** docs は英語を正とし、日本語版を `.ja.md` で隣に置く。README の冒頭に図解 2 枚を並べ、クリックで PDF。
- **HOW:** 本人「日本人も見に来ると思うし」「このチェックスクリプトで何を行ってるのかがひと目でわかるようにな！（笑）」。
- **CONNECTION [in-session]:** 図解は a4-zukai スキルで作り、README 用に PNG を添えた（GitHub は PDF/HTML を埋め込めない）。
- **SCOPE:** 公開 OSS の入口の話。内部向けの文書の言語方針とは別。

### 6. 「スクリプトを流せば自分の環境を点検できる」は正しい。ただし限界を先に言う
- **WHAT:** Docker は判定の正しさを確かめるための道具で、利用者には不要。点検したいサーバーで走らせれば、そのサーバーが点検される。
  ただし: リリースが無いうちは Quick start が 404／Ubuntu・Debian 以外ではパッケージを判定しない／root でないと見えない範囲／
  そして**既知データの日付**（USN が出て利用者が更新しても、古い版のツールは「修正待ち」と言い続ける）。
- **HOW:** 本人「要するにこのリポジトリのスクリプトを自分で流せば、みんな自分の環境でのチェックはできる（と、思ってみんな見に来るはずなので）という認識で良いか？」
- **CONNECTION [in-session]:** データの古さへの対策として (a) USN が出たら即データ更新・再リリース、(b) PPA の版を `unreleased` で
  先に登録、を提示（母艦は changelog 確認を条件に (b) を推奨）。本人の判断待ち。
- **SCOPE:** 時点依存のデータで判定するツールすべてに付きまとう問題。30 日の古さ警告だけでは足りない場面がある。

### 論点転回記録（Pivots & Turns）

- **リリース直行 → 検収を挟む**
  - 転回前: CI が緑ならタグを打ってリリース、という段取り。
  - トリガー: 本人の「codex にレビューしてもらわなくていいか？」。
  - 転回後: リリース前に別系統の敵対的レビューを必須の工程にした。
  - 意味: 偽の安心を生む経路 2 件がリリース前に塞がった。
- **15 分で打ち切り → 待つ**
  - 転回前: 打ち切られたら範囲を絞って短く回す（母艦の当初案）。
  - トリガー: 本人の「2 時間かかっても…待つべきだろう？」。
  - 転回後: 時間制限を 2 時間に延ばし、絞り込みは時間を節約するためでなく、新しい指摘に時間を使わせるために行う。
  - 意味: 範囲を絞るのは時間の節約のためではなかった、と位置づけが変わった。
- **「修正が近い」を重く見る → 利用者の手段で線を引く**
  - 転回前: PPA に修正候補がある＝修正間近、とデータへの反映を考えかけた。
  - トリガー: 本人の「普通の人はそれ使わないよな」。
  - 転回後: 判定は変えず、備考で知らせるだけ。

## Key Learnings

- 本人の問いはどれも一行で、しかも（笑）付きだったが、毎回、母艦がその時点で採っていた段取りを止める位置に入った
  （リリース直行、短い打ち切り、PPA の重視）。軽い口調の問いを軽く扱わない。
- 母艦は「正しい表を出した」ことで説明を終えがちだった。表が正しくても読み方が無ければ「全滅？」と読まれる。
- サブエージェントの報告を検算せずに中継した誤り（PYSEC 番号）が一度あった。判定に効く主張は自分で取り直してから伝える。
