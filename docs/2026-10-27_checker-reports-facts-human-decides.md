# 点検ツールは事実を返し、判断は人がする

## Purpose & Context

- 起点はハンドオフの「Codex 4 回目の指摘 10 件を直す」。壁打ちとして始めたのではなく、各回の指摘の扱いを本人に判断してもらう
  質問のやりとりが、回を追うごとに「このツールは何に責任を持つのか」という問いに変わっていった。
- 外部入力: Codex の敵対的レビュー 4〜6 回目（毎回 GATE: FAIL）、プラグインの自動セキュリティレビュー（`--yes` の指摘）。
- 前提: 前セッションの壁打ち記録（結果の読ませ方・レビューの待ち方）と、依頼文の「偽の安心がいちばん避けたい失敗」。

## Insight Crystallization

### 知見 1: ツールが「保証」を引き受けると、レビューは収束せず、結果には留保が溜まる

- **WHAT**: 「他人のコードを実行しない」「偽の安心を出さない」をツールが**保証すべき性質**として扱うと、点検ツールにはそれを保証しきる手段が
  無いため、敵対的レビューは毎回 1 段奥の穴（本体の所有者 → ライブラリ → RPATH → 途中の symlink → 空の項目 → 継承される RPATH）を突く。
  そして穴を塞ぐためにツールが黙って下す判断（実行しない、確かめられないから UNKNOWN）が増え、それが結果に「誰も頼んでいない留保」として
  現れる。
- **HOW**: 6 回目も GATE FAIL になった時点で、私が規約（3 回で収まらなければ止まる）に従って A/B/C を提示し、「一般ユーザーも既定で実行しない」
  （B）を推奨した。本人の応答が転回点: 「チェックするのに必要な実行なら実行すればよい。実行の許可を理由とともに最初から明示すればよい。
  脆弱性をローカルでチェックするのが目的なのだから、必要なことはしっかりとユーザーに明示して、その結果をユーザーに返す。判断は人間が
  行えばよいだろ？ お前が判断までしようとするから変な留保が出てくるんだ」。
- **CONNECTION [in-session]**: Codex への依頼文に私自身が書いていた脅威モデル（"must never run their code … must never give false assurance"）が、
  穴の量産の源だったことを、この直後に私が言語化した。次の Codex 7 回目の基準を「事実の誤り／黙った抜け／示さない実行／余計な書き込み」に
  改めることも同時に決めた。
- **CONNECTION [in-session]**: 前回の「C」（リリース基準を決める）の中身が、本人の思想で決まった（基準はツールの責務の範囲で引く）。
- **CONNECTION [recording-time inference]**: グローバル規約の ETHOS「Generous Input, Rigorous Output」と、本人の「原本と写像」の語彙に重なる。
  ツールの出力（写像）が原本（ホストの事実）に対して誤っていないことには厳格に、原本をどう受け止めるかは人に開いておく。
- **SCOPE**: 「点検」ツールに限った話。権限を持って何かを**変える**ツール（`--output` の書き込み）は別で、そこはツールが厳格に防ぐ
  （`ln -T`、全階層の検査）。この区別は会話中に明示されたわけではないが、本人は `--output` の制限には一度も異を唱えていない。

### 知見 2: 「たぶん修正済み」ではなく「分かったこと／分からなかったこと」

- **WHAT**: 判定の確度を形容（「可能性が高い」）で表すのをやめ、何が見えて何が見えなかったかを書く。状態名（LIKELY_FIXED）は依頼文・JSON の
  語彙として残し、理由の文を「分かったこと: 修正のエラー名がある、辞書は 1 個。分からないこと: ファイル内のデコーダーがすべて修正済みか」にした。
- **HOW**: Codex 5 回目の指摘 6（辞書を共有する新旧 2 デコーダーは見分けられない）について、私が「LIKELY_FIXED を残すか UNKNOWN に
  するか」を問い、本人に「意味がわからない」と言われた。噛み砕いて再質問した結果の本人の答え: 「多分修正ずみ、何じゃなくて、わかったことと
  わからなかったこと（修正済みとは言えない可能性がある）をしっかりと出力すれば、それで事足りるだろ？」。
- **CONNECTION [in-session]**: 私の選択肢は二択（表示を残す／全部 UNKNOWN）だったが、本人の答えは第三の道（表示の問題ではなく中身の問題）だった。
  噛み砕いた説明で「どちらでも終了コードは 2 で、違うのは表示だけ」と書いたことが、二択が本質でないことを露出させたと思われる（推測）。
- **SCOPE**: 状態名を残す判断は私がした（依頼文・JSON との互換のため）。本人はそこに異を唱えていないが、明示の同意でもない。

### 知見 3: 点検は「永遠の正しさ」を保証しない — 権限の問題は指摘として出す

- **WHAT**: 他人が書き換えられる既知データ（`--data`）を root で使うかという問いに、拒むのではなく「権限の問題がある」という事実を結果の冒頭に出す。
- **HOW**: 私は最初「root では拒むか」と問い、本人は前提を誤読（「チェックのプログラムがなぜ root で他人のファイルに書き込むのか」）。読む側の話だと
  説明し直すと、本人の答え: 「調査時点で修正されているなら、後で誰が書き換えようがこっちの知ったことではない。誰でも書き換えられるところにある
  なら、パーミッション問題の指摘やそういったことを、指摘として出力すれば良いだけ。チェックすることが目的で、あなたがすべての正誤判定を永遠に
  保証するわけではないのだから」。
- **CONNECTION [in-session]**: 知見 1 の前触れ。この時点で本人はすでに「保証」と「指摘」を分けていたが、私は実行の扱いには広げなかった（6 回目まで規則で守り続けた）。
- **SCOPE**: 本人の第一文（「後で誰が書き換えようが知ったことではない」）は、私の説明の時点とは別の局面（調査後の改変）を指しているようにも読める。
  結論（指摘として出す）は明確なので、実装はそれに従った。

### 知見 4: 同意は「見せてから聞く」で成り立つ — `--yes` は見ないことへの同意

- **WHAT**: 実行の許可は、実行するもの・理由・事実を先に示して、人がその場で選ぶことで意味を持つ（本人がプレビュー付きの選択肢で「実行前に一覧を
  見せて確認」を選んだ）。`--yes` は「一覧を見ないで全部」という同意で、その意味を利用者が理解していることが前提になる。
- **HOW**: プラグインの自動セキュリティレビューが「root の `--yes` は他人のコードを root で動かす。ツールが除外すべき」と指摘。私は事実として正しいと
  認めたうえで、思想に沿う代替（`--yes=all`／`--yes=clean`）を出した。本人: 「Yes を選ぶときの注意事項を README に丁寧に記載しておけばいい。何を
  目指すのかを根本で持っていれば悩むところではない。root で動かすことが何を意味するのかも理解していない人が Yes でやると、結果も読み間違える。
  だから、Yes で一気に回したらこういうことになるよ、と分かりやすい言葉で（言い訳っぽくない書き方で）丁寧に書いてあることが大事」。
- **CONNECTION [in-session]**: 「結果も読み間違える」が要点。実行の危険だけでなく、他人が変えられるプログラムが答えた版をそのまま信じる危険。
  README には「プログラムが答えた版は、そのプログラムと同じだけしか信用できない」と書いた。
- **CONNECTION [recording-time inference]**: 前セッションの壁打ち（結果の読ませ方）と同じ系譜。ツールの出力が正しくても、読み手が前提を持たないと
  誤読される。注意書きは免責ではなく、読み方の説明。
- **SCOPE**: コードは変えていない（`--yes` は一覧すべて）。「言い訳っぽくない」は文体の要求で、私はできるだけ「何に同意するか」を事実で書いたが、
  本人の確認はまだ。

### 知見 5: 実行を見える化すると、テストでは見えない回帰がすぐ見える

- **WHAT**: 実行一覧を結果に必ず出す形にした最初の実機の実行で、「`/home/…/.local/bin/mise --version（C04 node）`」が一覧に現れ、symlink の別名を拾う
  修正の回帰（mise の shim を node として扱う）がすぐ分かった。単体テストは全部通っていた。
- **HOW**: 端末での確認のテストが落ちた原因を手で再現したときに、一覧の 2 番目に mise が出ていた。
- **CONNECTION [in-session]**: 同じセッションの変異テスト（修正を戻してテストが落ちるか）も、「全部通った」の中身を露出させた（4・5 回目の修正 25 個のうち
  作業中に 6 個が当初捉えられておらず、テストを直した）。テスト記録を作る段階でも、推測で書いた番号が実測と違っていた。
- **CONNECTION [recording-time inference]**: 知見 1 と同じ根。黙って判断する代わりに見せると、作り手自身の誤りも見える。透明性は利用者のためだけでなく、作り手の検証手段になる。
- **SCOPE**: 1 事例。見える化が常に回帰を露出させるわけではない。

### 論点転回記録（Pivots & Turns）

1. **「root では既定で実行しない」（4 回目後・本人も選択）→「実行は事実を示して人が選ぶ」（6 回目後）**
   - 転回前: 実行の危険はツールの規則（所有者・依存の検査）で防ぐ。root はさらに既定で止める。
   - トリガー: 6 回連続の GATE FAIL と、私の「B（一般ユーザーも既定で実行しない）」の推奨に対する本人の反論（知見 1 の引用）。
   - 転回後: ツールは必要な実行を、理由と事実とともに先に示し、同意を得て実行する。規則で決めるのをやめる。ldd も同意の外で実行に近いので廃止。
   - 意味: 4 回目後に本人が選んだ判断を、本人自身が思想から置き換えた。判断の主体を「ツール」から「人」へ移した転回で、脅威モデル（Codex への依頼文）も変わる。

2. **二択の質問 → 本人が第三の答えを出す（指摘 6）**
   - 転回前: LIKELY_FIXED を残すか、UNKNOWN にするか。
   - トリガー: 「この質問の意味がわからない」→ 噛み砕いた説明（どちらでも終了コード 2、違いは表示だけ）。
   - 転回後: 表示を選ぶ問題ではなく、分かったこと／分からないことを書く問題。

3. **「root で拒むか」→「指摘として出す」（`--data`）**
   - トリガー: 本人の前提の誤読（書く話と読む話）を説明し直したあとの、「点検は永遠の正しさを保証しない」。
   - 意味: 知見 1 の前触れ。私はここで実行の扱いに一般化しなかった。

4. **「ツールが `--yes` から除外する」（自動レビューの案）／「`--yes` を 2 つに分ける」（私の案）→「README に丁寧に書く」**
   - トリガー: 本人の「何を目指すのかを根本で持っていれば悩むところではない」。
   - 意味: 思想が決まっていれば、新しい指摘ごとに規則を足す必要はない。迷ったら根本の目的に照らす。

## Key Learnings

- **質問の立て方**: 英語で出した（本人「なんで英語で俺に聞いてくるのか」）、抽象的な二択で前提を書かなかった（「意味がわからない」）、
  読む側の話を書く側と誤読された（Q2）。効いたのは、前提から噛み砕く→違いが実際どこに出るか（終了コード・表示）を具体的に書く→
  画面の見本（プレビュー）を付ける、の順。プレビュー付きの質問には一度で答えが返った。
- **止まるタイミング**: 規約の「3 回で収まらなければ止まる」を 6 回目で使った。もっと早く（4 回目の指摘 1 の時点で）脅威モデル自体を本人と
  見直してもよかった。4 回目後の root の既定停止は、本人の思想の言語化を待たずに私が推奨したもの。
- **推奨のずれ**: 私の推奨（B: 実行をもっと止める）は、本人の思想（必要なら実行し、示して、人が決める）と逆向きだった。「安全側＝実行しない」と
  一方向に倒す癖があった。点検ツールでは「実行しないこと」も、版を弱くし、留保を増やす選択だった。
- **記録の規律**: テスト記録の番号を推測で書いた（実測と違った）。「記録は実測で作る」を本人の「今のうちに」に応える形で守れたのは、取り直したから。
- **長い文脈の後半**: 本人の規約にある「後半で performative に寄るクセ」。今回は後半ほど本人の思想に引き戻された。自分から根本を問い直すより、
  指摘ごとに規則を足す方向に流れていた。

## Current Position

- 合意: 点検ツールの責務は「必要なことを示し、事実を返し、人が判断する」。実行は示して同意を得る（端末で選ぶ／`--yes`／`--no-exec`）。
  確度の形容ではなく、分かったこと／分からないことを書く。権限の問題は指摘として出す。`--yes` の意味は README に丁寧に書く。
- 未解決: Codex 7 回目を新しい基準で回すと収束するか。事実の網羅性（dlopen・設定ファイル・`$LIB`）をどこまで書けば「事実として誤り」にならないか。
  README の注意書きの文体が本人の意図（言い訳っぽくない）に合っているか。状態名 LIKELY_FIXED を残した判断（私の判断・本人の明示同意は未）。

| 仮説 | 状態 | 根拠・留保 |

| 見せる形（実行一覧）は作り手の誤りも露出させる | 部分的に検証済み | mise shim の回帰が初回の実機実行で即発覚（1 事例） |
