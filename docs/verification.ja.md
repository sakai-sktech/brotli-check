## この試験が示すこと、示さないこと

試験では、判定が前もって分かっているコピーをコンテナや試験用のファイルにわざと入れ、ツールの結果を期待した判定と比べます。
このページに書いたイメージ・実行のしかた・ビルドでは、期待した判定とすべて一致しました。示すのはそこまでです。実際のホストでの
見つけ漏れや誤判定の率は測っていません。どんなビルド・ディストリビューション・アーキテクチャでも期待どおりに判定することも
示していません。

- 文字列による推定（C09）は、Ubuntu 24.04 の gcc 13（x86_64）でビルドした Brotli 1.2.0・1.2.1、Node.js の公式バイナリ、PyPI の

## 2026-11-04 以降の統合テスト

5 つのイメージと bash 4.2 は変わっていません。変わったのは、流し方と、確かめる中身です。

- **CI。** push と pull request のたびに、GitHub Actions が単体テストを流し、続けて 5 つのイメージと bash 4.2 を、Ubuntu 24.04 の
  runner の Docker で流します（7 ジョブ、2 つの契機を数えて 14 件。Docker の版はここには記録していません）。2026-11-04〜10 の各変更（上の表のその日付の行）の pull request と、
  下の統合テストの変更の最終の状態は、14 件すべて成功しました。（2026-11-07〜10 の変更の途中で、先に runner 自身の .NET の導入が原因で落ちた回があり、直しました。
  `main` で、イメージのビルド中に 1 回落ち、同じ内容で流し直したら通った回もあります。）
- **C14 を本物のコンテナエンジンで確かめる（2026-11-04 から。#6）。** C14 の段は、イメージのコンテナを起動し、`--inspect-containers` を 2 通りで流します。
  エンジンの unix ソケット越し（実行中のコンテナの中まで見る）と、`127.0.0.1` の TCP の中継越し（中は見られず、そう出す）です。2026-11-09 から（#27）は、
  コンテナの中の Python のモジュールも確かめます。PyPI の Brotli 1.2.0 は `VULNERABLE`、1.2.1 は `FIXED` で、5 イメージとも同じでした。
- **C14 の終了コード（2026-11-13 から）。** unix ソケットの回は終了コード 1（コンテナの中に修正前のコピーがある）、TCP の回はちょうど 2
  （C14 の `failed` が 1 件だけで、ほかの所見は無い。ツールはイメージの使い捨てのコンテナの中で、`/opt` と `/srv` を隠して流すので、
  試験を流すホストが持つものに終了コードが左右されない）、同じ回を `--containers` だけで流すと 0（同じ文で種別は `chosen`）を期待します。
  それまでは、終了コードが 3 でないことしか見ていませんでした。期待値を 1 つずつ変えると（1 を 2、2 を 1、0 を 2）それぞれ失敗し、
  存在しない Node.js の版を指定すると、ビルドの失敗は失敗した段とダウンロードのエラーを出しました。2026-11-13 に 5 イメージと bash 4.2 が成功し、
  イメージを 1 つずつ流しても成功（50 件）、CI でも 5 イメージが 1・2・0 になりました。イメージのビルドが失敗したときは、ログの末尾を標準出力に出します。
- **どのエンジンか。** 2026-11-07〜10 と 2026-11-13 の手元の実行は、開発用の端末の Docker Desktop のエンジンが止まっていたので、`/var/run/docker.sock` の
  ネイティブの Docker エンジン（Docker 29.9.3）で行いました。CI は runner のエンジンです。**C14 の TCP の段はネイティブのエンジンが前提**です
  （ホストのネットワークのコンテナから、試験を流すホストの `127.0.0.1` に届く必要があるため）。**Docker Desktop では試していません**。届かないときは
  クライアントの出力とともに FAIL で止まる見込みです。上の 2026-10-26・27 の Docker Desktop での実行は、この段が今の形になる前のものです。

## 同梱コピーの文字列による推定（C09）

Ubuntu 24.04 の gcc 13（x86_64）で Brotli 1.2.0 と 1.2.1 を共有・静的ライブラリで（-O2 と LTO、strip の有無）ビルドしたもの、
Node.js 公式の 22.23.3／22.23.4／24.22.0／24.22.1、PyPI の Brotli と brotlicffi の wheel で試しました。その中の修正済みのものには
すべて `_ERROR_FORMAT_BLOCK_SWITCH` があり、未修正のものにはありません。試したビルドの中で判定できなかったのは、LTO と不要部分の
削除を使い、かつ `BrotliDecoderErrorString` を呼ばないプログラムだけで、そのときは `VENDORED_COPY` とします。1.0.x・1.1.x の
ビルド（修正版の 1.0.10 と 1.1.1 はソースに同じ印がある）、ほかのコンパイラ・アーキテクチャは試していません。ファイルの中の
2 つのデコーダーが辞書を共有している場合など、ビルドによらず見分けられないものもあります（[limitations.ja.md](limitations.ja.md) の
「文字列による推定」）。`tests/fixtures/c09/reproduce.sh` を空の状態から再実行すると、fixture はバイト単位で一致しました。
詳細とダウンロードの SHA256: [tests/fixtures/c09/README.md](../tests/fixtures/c09/README.md)。
